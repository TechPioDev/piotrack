## The honesty line for this stage

This stage is the one where §38 matters most, because AI features _look_ finished whether or not
anything real is behind them. Two rules were applied throughout:

1. **Fixture vs live.** The whole platform runs on a deterministic `fixture` model driver. Everything
   around the model — prompt versioning, cost accounting, credit limits, retries, persistence, parsing,
   the confirmation gate, every dashboard figure — is real and tested. The live OpenAI/Anthropic drivers
   are real code but **untested** (no credentials) and are labelled _Implemented (untested)_. The UI
   states plainly when output came from the fixture model so it can never be mistaken for inference.
2. **Mechanism vs judgment.** Where the feature's value is the _mechanism_ (a chat loop, a summary
   stored on a record, a proposal routed for approval, a drafted email), fixture-driven tests genuinely
   prove the feature — those are **Tested**. Where the feature's value _is the model's judgment_
   (AI lead scoring, opportunity scoring), a fixture proves only the plumbing, so those are
   **Partially Implemented**, not Tested. That line is drawn deliberately rather than rounding up.

## Architecture delivered

- **Data model** (7 new tenant-scoped tables + 1 extension): `ai_prompt_templates` (unique key+version),
  `ai_requests`, `ai_actions`, `ai_conversations`, `ai_messages`, `ai_prompts` (AIVIS library), and
  `ai_visibility_checks` extended with `ai_prompt_id` + `recommended`.
- **`AiProvider`** contract + `AiCompletion` + `AiProviderManager` + `config/ai.php`;
  `FixtureAiProvider` (tested, deterministic, shapes responses per feature so parsing is exercised),
  `OpenAiProvider` / `AnthropicProvider` (real, untested), bound in the container.
- **`AiGateway`** — the single choke point. Nothing calls a provider directly, which is what makes the
  governance non-bypassable: it renders the active prompt version, refuses the call when credits are
  exhausted _before_ any spend, retries only transient failures, records tokens + estimated cost, bills
  usage only on success, and audits both outcomes.
- **`PromptRegistry`** — nine built-in prompt defaults seeded on first use; publish creates a new
  version, activate rolls the pointer, exactly one active version per key.
- **`AiActionService`** — propose → confirm → execute, with rejection terminal, execution idempotent,
  and CRM writes restricted to an allow-list. There is no configuration flag that permits autonomous
  execution of a sensitive action.
- **`AiSalesAgent`** — sixteen sales capabilities, split so that anything which changes data or reaches
  a third party is only ever proposed.
- **`AiVisibilityDashboard`** — library runs across five engines (idempotent per day), share of voice,
  three frequencies, competitor comparison, three dimension breakdowns, trend and change alerts.
- **`ai:run-visibility-checks`** scheduler (daily 03:00, entitled tenants only).
- **RBAC + entitlement**: 4 `ai.*` permissions with a deliberate split — `ai.agent.use` may _propose_,
  only `ai.actions.approve` may _confirm_. New `Feature::Ai` (Professional+); AIVIS rides the existing
  `ai_visibility` entitlement. 21 routes.
- **UI**: sidebar **AI** group; 6 Inertia pages (overview/usage, sales agent, conversations, action
  queue, prompt templates, AI visibility).

## Defects discovered & fixed

- **Session flash was never shared with the frontend — every confirmation message in the app has been
  invisible since Stage 2.** `HandleInertiaRequests::share()` had no `flash` key and no page read one,
  so all **147** `->with('status', …)` calls across Stages 2–12 (contact created, campaign sent, plan
  activated, …) silently went nowhere. Surfaced while wiring the AI agent's result panel. Fixed by
  sharing `flash.status` + `flash.ai_result`, typing it on `SharedData`, and adding a dismissible
  `FlashMessage` banner to the authenticated layout so it renders on every page. Covered by three new
  tests asserting the props actually arrive.
- **The Analyst role never received `analytics.view`** (a Stage 11 oversight found while mapping AI
  roles): the role whose entire purpose is analysis could not open the Analytics module. Stage 11's
  edits landed those permissions on MarketingUser/SalesRep/Viewer but skipped Analyst, and no test
  covered it. Analyst now has analytics view + experiments + growth-score manage.
- `bookings.booking_page_id` is non-nullable, so an approved `book_meeting` action would have failed at
  execution time; it now falls back to the tenant's first active booking page and reports honestly when
  none exists.
- PHPStan (19): `Entitlements::has()` → `feature()`; non-exhaustive match; aggregate-alias property
  access; nullsafe-before-`??` on non-nullable relations (switched to the codebase's FK-guard idiom).

## Manual QA

The AI platform was exercised through its tests rather than a browser session (browser login requires
entering a password, which is outside the assistant's allowed actions). What that verification covers is
the substance of the stage: the credit ceiling refusing a call before any provider is reached, retry and
failure accounting, the confirmation gate refusing to execute unconfirmed proposals, the field allow-list
discarding a proposal's attempt to rewrite `email`/`lead_score`, and every dashboard figure computed from
recorded checks. All six pages type-check and lint clean and render under test via their Inertia routes.
